01 / CONTEXT

The problem worth solving.

Payment percentages alone do not explain whether a project can fund its costs. Timing, reserves, delayed receipts, and earlier expenses all change the cash position.

02 / ARCHITECTURE

How the pieces connect.

The workflow takes uploaded or entered payment terms through source confirmation before calculation. A shared event ledger then drives the cash timeline, stress transformations, and candidate advance schedules. Changed inputs invalidate old results.

03 / CONTRIBUTION

What I built.

  • Built document intake and a source-review checkpoint before calculation.

  • Developed bounded schedule search and explicit stale-result invalidation.

04 / ENGINEERING CHOICES

The decisions behind it.

Exact amounts, explicit ordering

Money uses Decimal with two decimal places. Outgoing events precede incoming events on shared dates so a temporary reserve breach remains visible.

Confirm before calculating

Rule-based extraction is the default. Optional semantic extraction needs provider configuration and still requires review of material fields.

Bound the answer

The search uses chosen dates and disclosed bounds. A no-match result means none of the tested candidates worked, not that every possible schedule is infeasible.

05 / BOUNDARIES

What this does—and what needs care.

One currency per deal; no tax, FX, holiday, or business-day modeling. Data is held in the browser tab and request memory. This is conditional decision support, not a prediction or guarantee of payment.
